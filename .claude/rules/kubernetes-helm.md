# Kubernetes + Helm rules (`deploy/helm/**`)

Authored 2026-08-07 from the failures a real chart rewrite produced (#2194
and its siblings). Every rule below exists because its absence caused a
concrete defect in this repo — none is generic advice.

**No openEHR spec governs deployment — this is entirely our own design.**
The authority here is the official Kubernetes, Helm and Artifact Hub
documentation. Cite it the way spec work cites the vendored specs: a URL and
the section, in the template comment or the PR.

## The prime rule: a rendered field is a CLAIM, and a claim is verified

`helm template` proves the chart produces YAML. It proves nothing about
whether Kubernetes honours that YAML. Three of this session's defects
rendered perfectly and were wrong on a cluster. **Rendering is never
acceptance.** Acceptance is `helm upgrade --install` on a live cluster, the
behaviour observed, and the observation quoted in the PR.

That acceptance is now an INSTRUMENT rather than a habit:
**`scripts/deploy-probe-k8s.sh`** installs the chart on a real cluster and
reads each answer from the layer that actually decides it — the container
runtime's own spec for the security posture, the API server for admission, the
EndpointSlice for readiness. Run it for any chart change with behavioural
reach and quote its record. The record is NOT in the tree: the harness writes
`kubernetes.json` under `docs/conformance/deployment/`, which is gitignored
there on purpose (a record measures ONE system under test, and a committed
file would invite comparing runs that measured different images, overlays and
profiles; the reasoning lives in `docs/conformance/deployment/README.md`). So a
quoted record comes from exactly one of two places, and the quote says which:
the artifact the CI job uploaded for a named run, or the local run you
performed for this change. Either way, quote the SUT identification the
harness prints beside it (the image reference and the overlays/profiles it
drove); a record without its SUT is the failure the ignore exists to prevent,
and a file left on disk by an earlier local run describes a different system.
The `/k8s-test` skill stays the manual procedure for what the harness does not
cover, and the harness declares those gaps in its own output.

## 1. Version-gate every field against the declared `kubeVersion` floor

An API server **silently prunes** a field its schema does not know, and a
beta field behind a disabled gate is **accepted and ignored**. Both produce a
chart that installs cleanly while the safety property it claims does not
exist — the exact silent-wrong-behaviour class `reliability.md` legislates
against, one layer down.

**Before adding any field to a manifest, establish the release it became
available in, from the KEP itself:**

```bash
gh api -H "Accept: application/vnd.github.raw" \
  "/repos/kubernetes/enhancements/contents/keps/<sig>/<nnnn-name>/kep.yaml" \
  | grep -A5 '^milestone:'
```

That file is generated by the enhancement process and states `alpha`,
`beta` and `stable` milestones plus the feature-gate name. The docs site is
**not** a substitute: once a feature goes GA the version note is *removed*
from the reference page, so the current page for a field added in 1.31 reads
exactly like one for a field that has existed since 1.0.

The rule: **a field may only be rendered unconditionally if its `stable`
milestone is at or below the chart's `kubeVersion` floor.** Otherwise it is
gated on `.Capabilities.KubeVersion` at the release where it *takes effect*
(GA, or beta — beta gates are on by default), or the floor rises. Never
rendered and hoped for.

Gating at beta rather than GA is a deliberate trade, and the template comment
says so: beta gates are `disable-supported`, so a cluster that turned one off
gets the API default silently. That residual gap is worth naming in the
comment; it is much smaller than withholding the field from every cluster
between beta and GA, where it demonstrably works.

The floor is `>=1.36.0-0`, and the reasoning must be stated precisely, because
the loose version of it is wrong. 1.36 is **not** "the supported window":
upstream supports three minors, so this floor is the window's TOP and an
operator one minor back cannot install the chart. It is chosen because it is the
release where the newest field the chart renders (`hostUsers`, KEP-127) went
stable. That makes it a genuine COMPATIBILITY floor rather than a support
opinion, and it makes every other field the chart renders unconditional.

Gating is the tool for a field genuinely newer than the floor; **raising the
floor is usually the better answer**, because a gate is a silent absence and a
floor is a loud refusal. Raising it costs the operators below the new floor, so
the trade gets stated in `Chart.yaml` rather than implied.

Keep the field-to-KEP table in `Chart.yaml` current: it is the evidence for the
floor, and the next person to add a field needs to see where the ceiling
already is.

`kubeVersion` is a promise about what the chart *does*, not a guess about
what an operator runs. Widening it is a breaking change; narrowing it is a
bug fix.

## 2. Immutable fields are load-bearing, and the gate is not optional

Some fields cannot be changed after creation, so a diff that looks harmless
fails **only on upgrade of an existing release**, which no fresh-install test
and no render check ever reaches:

- **`Deployment.spec.selector.matchLabels`** — "cannot be changed once
  created" (<https://kubernetes.io/docs/concepts/workloads/controllers/deployment/>).
  This is the live trap: the natural way to distinguish a second workload's
  pods is to add a `component` label to the shared `selectorLabels` helper,
  which silently breaks `helm upgrade` for every existing release. Add the
  label to `ferroehr.labels` (metadata) — **never** to `ferroehr.selectorLabels`.
- `Service.spec.clusterIP`, StatefulSet identity fields, PVC shrink.

`deploy/helm/validate.sh` `assert_selector_stable` pins the expected selector
key set and checks that no Service or PodDisruptionBudget selector matches two
workloads. It is DERIVED rather than tabulated — `deploy/helm/gates/selector.jq`
reads every rendered workload that carries a pod template — so a new workload
needs no gate edit. What it does need is a RENDER: the gate only judges
workloads some values file produces, so a workload no `ci/*-values.yaml`
enables is a workload the gate never sees. Adding a workload therefore means
adding a values case (§8), not a table row.

## 3. A gate that greps the file passes vacuously

`assert_security` once grepped the rendered file for field strings. With one
workload that is merely weak; with two it is *wrong* — a compliant container
anywhere in the file vouched for every other container, so a second workload
could ship non-compliant and the gate stayed green.

**Structural gates parse the YAML and iterate every object, every container.**
A gate must also **fail when it finds nothing to check**: a pod-less render
passing "all containers compliant" is a false green. Prove a new gate by
mutation — break the property deliberately, watch the gate fail *and name the
offending container*, then revert.

## 4. Diagnose against the DEFAULT render

A conditional branch is not the chart's behaviour. This session produced a
public misdiagnosis — probes reported as conflating liveness and readiness —
because the non-default `probes.exec` branch was read as if it were what
users get. **Render with stock values first**, and when reporting a defect
say which values reach it.

Corollary: an alternative that is *presented* as safer deserves more scrutiny,
not less. `probes.exec` looked conservative and was the broken path — it made
readiness never touch the database, so a pod with a dead database reported
Ready and took clinical traffic.

## 5. Probes mean specific things (and drive server design)

Per <https://kubernetes.io/docs/concepts/workloads/pods/probes/>:

- **liveness** — process-local only. Restarting cannot fix a dependency, so a
  liveness probe that checks one turns a database blip into a cluster-wide
  restart storm. Ours is a constant.
- **readiness** — checks dependencies; failing removes the pod from the
  Service **without restarting it**.
- **startup** — protects a slow boot from the other two.

If a server endpoint does not fit these roles, **the server is what changes** —
never the probe pointed somewhere convenient. `/health/liveness` and
`/health/readiness` exist in this shape for this reason; readiness
distinguishes "database reachable" from "database carries our schema" and
refuses traffic on the second.

## 6. The chart provisions no database

`docs/architecture.md` takes an external DSN (`database.existingSecret`); the
chart deploys no PostgreSQL. Two consequences that have each already bitten:

- **Never list an image the chart does not deploy** in
  `artifacthub.io/images`. Artifact Hub scans every entry and attributes its
  CVEs to us. `whitelisted: true` is not the fix — it silences the scan and
  leaves the false claim.
- **Live testing runs PostgreSQL in docker compose on the host**, with the
  chart pointed at it. An in-cluster `kubectl create deployment` has no PVC,
  so a restart returns an empty database and readiness correctly reports
  `migrations DOWN` — a self-inflicted diagnosis cycle, not a chart defect.

## 7. Pod Security Admission is the operator's job, and the chart must say so

The chart satisfies the `restricted` profile, but enforcement is a
**namespace label** no chart can set
(<https://kubernetes.io/docs/concepts/security/pod-security-admission/>).
Documenting satisfaction as a compatibility statement is a claim an operator
can act on by doing nothing. State it as an instruction, with the command, in
`NOTES.txt` (printed on install), beside the `securityContext` values, and in
the book.

Until that label is applied, nothing verifies the posture. A live test is only
evidence if it ran in an enforcing namespace — say which.

## 8. Version and release mechanics

- Helm **4.2.3**. Golden renders are not byte-stable across Helm minors, so
  the local toolchain and the CI lane must match or the compare skips itself.
- Chart `version` and `appVersion` are **independent SemVer lines**; the
  release procedure and its CI guards live in `changelog.md` §Helm chart —
  not duplicated here.
- Regenerate goldens with `deploy/helm/validate.sh --update` in the same
  commit as the template change; CI diff-guards them.
