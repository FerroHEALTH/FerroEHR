- Superseding a composition or a party no longer slows down as its history grows. The foreign-key check that every new node and attestation row makes against its version could scan all versions of the object instead of probing one, depending on the planner statistics at the time: on the storage bench, superseding an object with a few hundred versions took about 14 ms instead of 9 ms when the plan flipped. Migrations `clinical/0022` and `party/0013` re-key the version-tree uniqueness constraint `uq_version_tree` with the object id last, so the check always probes the primary key. The constraint enforces the same uniqueness as before.
