- Breaking: which clients count as backend clients and which reach the DEMOGRAPHIC API is policy the CDR holds, read on every request with no restart, never a configuration key. `[auth.smart] backend_clients` and `[auth.smart] demographic_clients` are removed, and a file or `FERROEHR__AUTH__SMART__*` variable that sets either is refused as an unknown key. A client's `system/aql-*` scope counts when the client's `AGENT` performs a `ROLE` whose capability codes `ferroehr-operations::query_system_wide`, and the DEMOGRAPHIC API admits a client whose `ROLE` codes `ferroehr-operations::access_demographic`, beside a caller holding `[auth] product_scope`. Both are new operations of the terminology, admitted by name in `[authz.grants] allowed`, whose default admits neither. A grant counts for the client's own app-only token; a person signed in through the client holds the person's grants. To move a deployment, write an `AGENT` carrying the client's `client_id` and a `ROLE` coding the operation through the Demographic API, and list the operation in `[authz.grants] allowed`; the book's "Operational policy" page has the worked example. `[auth.smart] patient_issuers` stays: it is trust, the issuers whose `ehrId` claim names an EHR of this platform.
