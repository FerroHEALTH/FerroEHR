- A population AQL query with a range filter on an event's time, a history's origin or a magnitude no longer slows down by orders of magnitude when the store has grown since its last `ANALYZE`, as it does while a store fills or after a new template's first compositions. cdr-benchmark's `bp_data_filtered` (`WHERE …/value/magnitude >= 140 ORDER BY … DESC`) ran for up to 23 s against 84 ms on fresh statistics, and the same filter without the `ORDER BY` read 2.3 M buffers for 500 rows where it now reads about 27,000. In a statement that does not stream, the filter's index entry is now the first matching row of each version, which PostgreSQL can probe per version. The check for an earlier matching row reads that version through its primary key, whatever the statistics say. The rows a query answers do not change.
