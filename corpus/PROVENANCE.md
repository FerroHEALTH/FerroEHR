# The shared breadth-corpora tree

Vendored clinical-model and fixture material read by the spec crates' gates,
the application tests, and the fuzz seeds: the ADL/OPT/XML breadth packs the
`openehr-adl` and `openehr-its` readers are measured against, the fixture
bodies the service and REST suites commit, the openPGP key the version-signing
conformance lane mounts, and the material `fuzz/seeds.sh` symlinks.

It is ONE tree, and it sits at the repository root, for two reasons that both
rule out per-crate homes. One vendor script produces TWO representations of the
same fetch — `scripts/vendor/ckm-archetypes.sh` pages the CKM library once and
writes each archetype as ADL 1.4 text for `openehr-adl` and as AM 1.4 XML for
`openehr-its`, under one provenance count — so splitting the destination would
split one script's output across two crates. And the readers are MANY: two spec
crates, three application crates, two shell scripts and the fuzz workspace all
read from here, so no single crate owns the set.

Each subtree keeps its own `PROVENANCE.md` with the upstream source, the pin
and the license:

| subtree | fetched by | record |
|---|---|---|
| `archetypes/ckm/` (ADL 1.4 + AM 1.4 XML) | `scripts/vendor/ckm-archetypes.sh` | `archetypes/ckm/PROVENANCE.md` |
| `archetypes/adl2/` (ADL 2 + 1.4 twins) | `scripts/vendor/adl2-archetypes.sh` | `archetypes/adl2/PROVENANCE.md` |
| `templates/ckm/` (curated pack + full library) | `scripts/vendor/ckm-templates.sh` | `templates/ckm/PROVENANCE.md` |
| `templates/*.opt` | generated by the conformance instrument | this file, below |
| `fixtures/service/` (EHRbase v2.33.0 import) | hand-maintained, no script | `fixtures/service/PROVENANCE.md` |
| `ferropulse/` (the usage report v2 JSON Schema + examples) | `scripts/vendor/ferropulse-schemas.sh` | `ferropulse/PROVENANCE.md` |
| `veredictum/adl2-content/` (the catalogue's ADL 2 content cases) | `scripts/vendor/veredictum-adl2-content.sh` | `veredictum/adl2-content/PROVENANCE.md` |
| `fixtures/**` (the rest) | hand-authored / generated conformance material | this file, below |

The discipline is `.claude/rules/vendored-corpora.md`: verbatim, never
hand-edited, refreshed only by re-running the script.

## History: this tree used to live under the conformance instrument

Until 2026-08-26 the corpus sat inside `tools/cnf-runner/artifacts/corpus/`,
because the instrument was a crate in this workspace. The instrument is now the
independent [Veredictum](https://github.com/Vernum-Projecten/Veredictum) project,
consumed at the pin `scripts/lib/veredictum.sh` records, and the split follows
who READS each pack:

- The breadth packs here have no reader in Veredictum at all — the ADL 1.4 CKM
  pack, the AM 1.4 archetype-XML pack, the ADL 2 pairs and the full CKM OPT
  library are exercised only by this repository's gates, so they belong here.
- The catalogue-side records stayed with the instrument: the per-file corpus
  manifest (`MANIFEST.yaml`), the generated-set recipe contracts (`recipes/`)
  and the synthesized-OPT generator (`templates/generate_content_opts.py`) are
  Veredictum's, and are reached in the pinned checkout.
- `fixtures/**` and `templates/ckm/` are read by both, so both carry
  them. Pointing this repository's `cargo nextest` at a cloned external tree
  would make an offline test run impossible and would take the published spec
  crates' own suites with it.

The synthesized `templates/*.opt` files are the committed output of the
instrument's `templates/generate_content_opts.py`, whose emission mirrors
Veredictum's `src/exec/opt_synth.rs`; regenerate them from the pinned checkout
rather than by hand.

## Demographic operational templates under `fixtures/opt/valid/`

- `role.v2.opt` is the `Role.v2` operational template a deployed openEHR
  platform uses for its shared ROLE parties (root
  `openEHR-DEMOGRAPHIC-ROLE.Role.v1`), supplied by the owner on 2026-10-24
  and committed verbatim. It carries no patient data. It is kept because it
  is a real-world shape: single attributes whose children state `0..*`
  (#3994) and a `CONSTRAINT_REF` to an `ac0001` its ontology does not define.
- `person.v2.opt` is synthetic, written for the FerroEHR test suite: a minimal
  PERSON template with an identity and a `relationships` node, the partner a
  ROLE template is used with.
