== The Draft Terminology

The groups of this package and of the Access Log Information Model are coded in one draft terminology:

[horizontal]
Terminology identifier:: `openehr_access`, the value of `Terminology_id_access` in the invariants of both packages
Name:: openEHR access (draft)

The identifier is a `TERMINOLOGY_ID` of the form BASE gives (xref:BASE:base_types:identification.adoc[Identification], `TERMINOLOGY_ID`), and of the form openEHR gives its own code sets, such as `openehr_normal_statuses`. It carries no version part, since a code never changes meaning. An archetype binds a code of it in its `term_bindings` by the URI `http://openehr.org/openehr_access/id/<code>`, on the model of openEHR's own `http://openehr.org/id/<code>`; the URI is proposed with the identifier. The `openehr_` prefix is openEHR's namespace: the identifier is proposed and is not assigned. If openEHR adopts the groups, they move into the openEHR Terminology with numeric codes, `Terminology_id_access` becomes `openehr`, and `openehr_access` is retired. Until then each code is its own rubric, and a code that appears in more than one group is one concept.

== Codes from HL7 Code Systems

Where an HL7 code system publishes a code with the same meaning as a term of a group, the group's term is that code, and a record carries it under the code system's terminology identifier. The draft holds no code of its own for it. A URI or an OID is no valid `TERMINOLOGY_ID`, so the identifier of an HL7 code system is `HL7_` followed by the code system's `name`, on the model of openEHR's identifiers for external terminologies, which join the publishing organisation and the name with an underscore (`ISO_639-1`, `IANA_media-types`). This table is the one place a code system's canonical URL appears; an exporter to FHIR maps the identifier to the URL through it and keeps the code. The rule and the identifiers are proposed and not assigned.

A group is the set of its terms, whichever terminology each is of, so `has_code_for_group_id` in an invariant holds for each term the group lists below.

The groups `access default`, `access directive kind`, `access effect`, `access relationship`, `care path`, `access caller kind`, `access conflict`, `access value set binding` and `access log withheld` have constants on `OPENEHR_TERMINOLOGY_GROUP_IDENTIFIERS`, since the invariants of the package name them. The others are read from the Demographic IM and from a system's access record, where the RM has no coded attribute to bind them to: a system finds a care relationship, a representation or a kinship by the code in a relationship's `_name_`, its content by the code in each element's `_name_`, a record subject and a composition's episode by the code in an element's `_name_`, and a care team by the `group kind` code in a `GROUP`'s `_name_`, never by its archetype or a path. The Demographic IM makes a party's type its name (`PARTY.type()`, invariant `Type_valid: type = name`; `PARTY_RELATIONSHIP.type()` likewise) and names "the specialist care team, e.g. cardiology team" as the typical `GROUP` (`GROUP` class), so a coded name says what kind of group or relationship it is; the codes are this proposal's design. A professional role is no code of these groups: it is the coded `_name_` of a `ROLE`, in the terminology the jurisdiction names, and a sensitivity a caller may read and a purpose it may declare are rules of the controller's policy. The caller kind `access_service` is a caller acting through the electronic health data access services of EHDS Art 4 and 12, which an Art 10 opt-out binds.

`Terminology_id_confidentiality` in the invariants is `HL7_Confidentiality`.

A system that keeps the access log of the Access Log Information Model records a refusal of this procedure in `ACCESS_OUTCOME._reason_` with its `access refusal` code, which is that model's reason for an opt-out or a restriction. `ACCESS_LOG_RESTRICTION._accessor_kinds_` is coded in that model's `accessor kind` group, so a restriction names exactly the kinds its entries record. The Access Log Information Model lists its own groups on its Terminology page, in the same terminology.

== Value Sets

What a care role, a basis of representation, a kinship, an organisation type or a purpose is called in a jurisdiction is content of that jurisdiction (xref:BASE:architecture_overview:security.adoc[Security Policy], Privacy), and the package ships none of it. The controller binds each coded attribute to a value set in `ACCESS_POLICY._value_sets_`, held on a terminology server, and a system checks a code against the bound value set on that server. Where the policy binds none, the attribute takes any code of the code system below, and the system compares codes by terminology identifier and code:

[cols="2,3,3", options="header"]
|===
|Binding |Code system without a binding |Used by

|care_role
|`HL7_ParticipationType`
|the `care_role` element of a care relationship; `ACCESS_ACTOR_SCOPE._care_roles_`; `ACCESS_RELATIONSHIP_VALIDITY._roles_`

|representation_basis
|`HL7_RoleCode`
|the `basis` element of a representation

|kinship
|the openEHR Terminology group `subject relationship`
|the `kinship` element of a `related_to` relationship; `ACCESS_CONFLICT_RULE._kinships_`

|organisation_type
|none: the controller binds one before a rule names a type
|`ACCESS_ACTOR_SCOPE._organisation_type_`; `ACCESS_RELATIONSHIP_VALIDITY._organisation_types_`

|care_purpose
|`HL7_ActReason`
|`ACCESS_POLICY._care_purposes_`

|emergency_purpose
|`HL7_ActReason`
|the purposes the system reads as declaring an emergency
|===

`HL7_ParticipationType` defines the parts a professional plays in an act: for example `RESP` is "the person or organization that has primary responsibility for the act" and `SPRF` "a person assisting in an act through his substantial presence and involvement". `PART`, "the target of the participation is involved in some manner in the act, but does not qualify how", is the role a writer states when it knows none, so every care relationship has a role. No role implies another: a rule lists every role it means. The examples on these pages use these codes and fictional parties; they are no default list.

== Mappings to Standard Codes

A draft code whose closest standard code is broader or narrower stays in `openehr_access`. So does a code by which a system reads an access meaning into demographic content, such as `member_of`: a record coded with the broader standard code, in an archetype of its own, keeps the meaning that code system gives it and takes none from this package. == Codes from Other Terminologies

Professional role, sensitivity, category and purpose-of-use codes are not part of these groups. They come from the terminology the jurisdiction names, such as the `HL7_ActCode` sensitivity policy codes, the EHDS categories and the `HL7_ActReason` purpose-of-use codes, and a system compares them by terminology identifier and code. This keeps the privacy levels "defined by standards or agreements within jurisdictions of use" (xref:BASE:architecture_overview:security.adoc[Security Policy], Privacy).

The confidentiality levels are the one exception: the package fixes `HL7_Confidentiality` and its order, `N` < `R` < `V`, in its own text, because the decision compares levels. The code system states the order itself: "Very Restricted (V) is the highest protection level and subsumes all other protection levels", and `N` is "less protective than V and R" (`HL7_Confidentiality` 5.0.0, definitions of `V` and `N`). The codes `U`, `L` and `M` of the same code system read as `N`.
