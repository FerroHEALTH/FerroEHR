[auth]

Authentication: bearer tokens of one or more trusted issuers, Basic credentials, or both. [auth] is the section every FerroHEALTH product shares, checked by the ferrohealth-smart crate. FerroEHR is a resource server: it checks tokens and never issues them.

[auth]
enabled = true
issuer = "https://keycloak.example.com/realms/ferroehr"
audience = ["ferroehr"]

[[auth.basic.users]]
user = "clinician"
password_hash = "$argon2id$v=19$m=19456,t=2,p=1$…$…"   # never a plaintext password
scopes = ["user/composition-*.cruds", "user/template-*.cruds", "user/aql-*.cruds"]

Warning

auth.enabled = true with no mechanism is a boot error. Such a server could only refuse every request while advertising an authentication scheme it does not implement, which RFC 9110 §11.6.1 forbids: a 401 challenge must name a scheme applicable to the target resource. Configure an issuer, configure [[auth.basic.users]], or set auth.enabled = false for a development server.

The key-set fetches verify the identity provider’s certificate against the platform trust store and follow no redirects. An identity provider whose certificate comes from a private CA is trusted once that CA is in the image’s system store or in a directory or file named by SSL_CERT_DIR or SSL_CERT_FILE. A key set that cannot be read when a token needs it answers 503, never 401: the server cannot decide, and a 401 would tell a caller with a valid token that its credential was refused.

A validated token must also carry a non-blank sub claim: the authenticated subject is stamped into the audit trail, so a token without one is refused with 401 rather than recorded under a placeholder identity. A bearer token outside the RFC 6750 §2.1 b64token alphabet is refused the same way, with 401 and error="invalid_token".

Opaque tokens by introspection

An authorization server that issues opaque access tokens is served with mode = "introspection". Each bearer token is posted to the issuer’s introspection endpoint (RFC 7662 §2.1), and the active response stands in for the JWT claims: sub, scope, the roles of role_claims, aud against audience and iss against the issuer. An inactive token is a 401. An endpoint that cannot answer is a 503, because the server cannot decide. An active response is reused until its exp, at most cache_max_age_seconds.

KeyTypeDefaultDescription
endpointURLunsetThe introspection endpoint; unset reads the introspection_endpoint of the issuer’s metadata. https, or http on a loopback host.
cache_max_age_secondsint60The longest an active response is used; 0 caches nothing.
cache_capacityint10000The most responses held at once.
clienttableunsetThe client authentication of the call (RFC 7662 §2.1), with the keys of an outbound grant: client_id and client_secret, private_key_jwt or mutual TLS (see the grant keys).
bearertableunsetA client credentials grant whose token authorizes the call instead (SMART App Launch 2.2.0, Token Introspection). Exactly one of client and bearer.
 
[auth]
issuer = "https://idp.example.org/realms/ferroehr"
audience = ["ferroehr"]
mode = "introspection"

[auth.introspection.client]
client_id = "ferroehr-rs"
client_secret_file = "/run/secrets/introspection-client"

The Basic-auth user store

[[auth.basic.users]] is an array of tables and therefore file-only: the environment grammar cannot spell an array index.

KeyTypeDefaultDescription
userstringrequiredThe user-id. Empty, or with a colon or a control character, is a boot error (RFC 7617 §2).
password_hashsecretrequiredArgon2id PHC hash ($argon2id$v=19$…), never a plaintext password. Boot-validated against the OWASP floor; see below.
password_hash_filepathunsetRead the hash from a file instead, for a mounted secret. A hash is an offline cracking target, so prefer this wherever the configuration file itself is not treated as sensitive. Exactly one of the pair is required.
scopeslist of string[]The SMART on openEHR scopes the user holds, checked on every route exactly like a token’s scope claim. A user with none is refused everywhere a requirement applies.
roleslist of string[]The user’s RBAC roles, upper-cased on authentication. A user with none holds no role and is refused wherever [authz.rbac] asks for one. The former [authz.rbac.basic_roles] table is refused at boot.

[auth.basic] itself takes one key beside the users:

KeyTypeDefaultDescription
cache_ttl_secondsint300How long a credential that verified is kept, so a repeat request skips the Argon2id derivation; 0 turns the cache off and checks every request. The entry is named by a keyed hash of user-id:password under a key drawn at boot, never the password, and only a credential that verified is kept, so a wrong password always pays the derivation. The cache holds at most 4096 credentials and empties at a restart. The TTL bounds how long a removed user keeps working, which matters only until the restart that applies the new user list. Argon2id is slow by design, so with the cache off its cost bounds how many Basic requests a core can answer.

Warning

Every password_hash must meet the OWASP Argon2id floor: m>=19456 (19 MiB), t>=2, p>=1, algorithm argon2id. Anything weaker (or a non-argon2id PHC string, or an unparsable one) is a boot error naming the user. This is checked at startup because the verifier takes its cost parameters from the stored hash, so a deliberately cheap hash would otherwise verify happily and silently weaken every password in the store. The floor is the OWASP Password Storage Cheat Sheet §Argon2id minimum.

An unknown user-id is checked against a decoy hash of the same cost, so the time a refusal takes does not say whether the user exists.

[authz]

Role-based (RBAC) and attribute-based (ABAC) authorization, and the patient-data assurance gate. The full evaluation order and design rationale are in Security.

[authz.assurance]: the assurance level patient data requires

Off by default. What it refuses and the 401 challenge it sends are described in Security.

KeyTypeDefaultDescription
claimstringacrThe token claim carrying the authentication context class; a dotted path reaches into a JSON object.
levelstable of string → low | substantial | highemptyMaps each value your identity provider puts in claim to an eIDAS level of assurance. A value the table does not name carries no level. File-only: the keys are usually URIs.
minimumlow | substantial | highunsetThe level a patient-data request must carry. Unset refuses nothing.
 
[authz.assurance]
minimum = "substantial"

[authz.assurance.levels]
"http://eidas.europa.eu/LoA/substantial" = "substantial"
"http://eidas.europa.eu/LoA/high" = "high"

Boot refuses a minimum with an empty levels table or with no value mapped at or above it (every patient-data request would be refused), a blank claim beside a declared table, and a levels value that is blank or carries whitespace, a quote or a backslash, because the refusal names the accepted values in one quoted, space-separated acr_values parameter (RFC 9470 §3).

[authz.professional]: the natural person behind a token

Absent by default, and tokens are then not judged on it. Present, a patient-data request whose token names no natural person is refused with 403, unless it is a client token acting for a named professional.

KeyTypeDefaultDescription
claimstringsubThe claim identifying the natural person; a dotted path reaches into a JSON object. A token lacking it is a client token.
client_tokenssub_is_client | claim_absentsub_is_clientHow else a client-credentials token is recognised. sub_is_client also treats a token whose sub equals its client_id or azp as a client token (RFC 9068 §2.2); claim_absent relies on the missing claim alone.
acting_for_claimstringunsetThe claim a client token carries the professional’s identifier in, such as act.sub. Unset refuses every client token on patient data.

The access record then carries the acting mode and the professional; see Audit trail. Both tables are reachable from the environment too (FERROEHR__AUTHZ__ASSURANCE__MINIMUM, FERROEHR__AUTHZ__PROFESSIONAL__ACTING_FOR_CLAIM), except the levels map.

[authz.abac]

KeyTypeDefaultDescription
enabledboolfalseMaster ABAC switch.
engineenum{cedar,remote}cedarEmbedded Cedar, or a remote decision point.
organization_claimstringorganization_idJWT claim carrying the caller’s organization.
patient_claimstringpatient_idJWT claim carrying the patient id. Set, it scopes every request to the patient it names (see below). Empty turns the patient scope off.
patient_namespacestringunsetThe subject namespace (EHR_STATUS.subject.external_ref.namespace) the patient ids in patient_claim are issued in. Set, a claim names the EHR whose subject is that id under this namespace. Unset, a claim names the EHR holding that id only when no other namespace holds the same id.
check_directoryboolfalseSubmit DIRECTORY (FOLDER) operations to the decision point. Engine-independent, so it works under Cedar as well as a remote PDP.

The patient scope. With ABAC on and patient_claim set, a token without that claim is refused with 403. With the claim:

  • A route that names an EHR (/ehr/{ehr_id}/…) answers 403 unless the claim names that EHR’s subject. An EHR that records no subject is in no patient’s scope and is refused.
  • Without patient_namespace, an id held under two or more namespaces names none of those subjects, so it reaches none of their EHRs. Set patient_namespace to read the claim in one namespace.
  • An AQL query returns rows only from EHRs the claim names, whatever the query selects, including SELECT e/ehr_id/value FROM EHR e.

After a query runs, the decision point receives the subject ids of every EHR the query touched as its patient attribute, so a patient-keyed policy applies to queries whether or not patient_claim is set. Without patient_namespace, a query that touches a subject id held under several namespaces is refused with 403, because a bare id would name both subjects.

  • [authz.abac.cedar]: policy_dir (path, required when engine = "cedar" and ABAC is on) and reload_secs (int, unset, an optional hot-reload interval).
  • [authz.abac.remote]: server (secret URL, required when engine = "remote", and it must end with /, because the policy name is appended; credentials embedded in it are redacted from every rendering), connect_timeout_ms (int, 2000), request_timeout_ms (int, 5000).
  • [authz.abac.remote.oauth]: calls the policy service as an OAuth 2.0 client instead of with the Basic credentials of server: FerroEHR obtains a token with the client credentials grant and sends it as a bearer token. The keys are those of [audit.fhir_feed.oauth] (token_endpoint or issuer, client_id, client_secret or client_secret_file, client_auth, scope, audience, resource). When the policy service refuses the token with 401, a new one is fetched and the decision asked once more; a token that cannot be obtained, or that is refused again, is no decision, and the request fails closed with a 500, never a 403. server with credentials beside this table stops startup.
  • [authz.abac.policy.<kind>]: one entry per resource kind, with kind ∈ ehr, ehr_status, composition, contribution, query, directory. Keys: name (string, the policy to evaluate) and parameters (list of enum{organization,patient,template}). A key that is not one of those six kinds is a boot error, and template is rejected on ehr and ehr_status, since neither carries a template.

Warning

With engine = "remote", every resource kind the enforcement point consults needs a policy entry: ehr, ehr_status, composition, contribution, query, plus directory when check_directory = true. A missing one is a boot error. At runtime a kind with no policy can only be denied, since there is no policy to ask and permitting would be a silent hole, so the misconfiguration is caught at startup rather than turning into blanket 403s on live traffic. The Cedar engine reads its policies from authz.abac.cedar.policy_dir and needs no entries here.

[signing]

VERSION signing. On by default in digest mode, with read-time verification of the server’s own signatures strict by default.

KeyTypeDefaultDescription
enabledbooltrueServer-side signing of committed versions.
modeenum{digest,pgp}digestA SHA-256 integrity digest, or an OpenPGP (RFC 4880) detached signature.
key_pathpathunsetArmored secret key; required for pgp (a boot error otherwise).
key_passphrase / key_passphrase_filesecret / pathunsetKey passphrase. At most one of the pair.
retired_key_pathslist of path[]Armored public keys retired from signing and kept for verification, so versions signed before a key rotation keep verifying.
verify_on_readenum{off,warn,strict}unset ⇒ strict when signing is enabledRead-time recompute-and-compare policy for the server’s own signatures.

retired_key_paths exists because a stored VERSION.signature records no key identifier and is an immutable committed fact that cannot be re-issued; keeping the retired public key is the only way history stays verifiable across a rotation, and a public key can verify but never sign. Its environment form takes a comma-separated list (FERROEHR__SIGNING__RETIRED_KEY_PATHS=/keys/a.pub.asc,/keys/b.pub.asc).

Note

verify_on_read resolves to strict when signing is enabled. On every read the server recomputes the signature of a version it signed and, on a mismatch, returns a 500 integrity fault rather than silently serving a provably corrupt record. Set it explicitly to warn (log + meter version_signature_invalid_total, still serve) or off (never check). Client-supplied signatures (an author’s own, or one carried by an imported version) are always stored verbatim and never re-verified, whatever this setting says, because the author may have signed a different agreed serialization.

Warning

pgp mode fails closed at boot if the key is missing or unusable: the server will not start. Verify the key and passphrase before switching modes.

Choose an Ed25519 signing key

The server refuses an ECDSA (P-256, P-384, P-521, secp256k1, Brainpool) or Ed448 signing key at boot: their private-key arithmetic runs on crypto-bigint 0.5, whose constant-time operations can branch on secret values (RUSTSEC-2026-0387), with no fixed release on that line. The boot error names the advisory. Move to Ed25519 with the steps below; the old certificate goes in retired_key_paths, where it keeps verifying, because verification uses only public values.

An RSA signing key is accepted, but it makes every commit perform an RSA private-key operation, the operation the Marvin timing sidechannel concerns (RUSTSEC-2023-0071 / CVE-2023-49092), for which the underlying rsa crate has no fixed release. An Ed25519 key keeps that code off the signing path entirely.

The server does not refuse an RSA key: a repository whose history is already RSA-signed needs that key to keep verifying, and signatures are immutable committed facts that cannot be re-issued. Instead it logs a warning at boot naming the advisory. To clear it:

  1. Generate a new signing key: gpg --quick-generate-key "…" ed25519 sign, and export the armored secret key to key_path.
  2. Export the public half of the old certificate and add it to retired_key_paths, so versions signed with it still verify (see above).
  3. Restart. New versions are signed with Ed25519; old ones keep verifying.

Rotation inside one certificate is cheaper still: add an Ed25519 signing subkey to the existing certificate, export the armored secret key again to key_path, and restart. The server signs with the newest subkey whose binding grants signing and that is neither expired nor revoked (the rule), with no retired_key_paths entry needed: the certificate keeps the previous subkey, so past signatures continue to verify. For a refused ECDSA or Ed448 key this works when the new Ed25519 subkey is the one chosen. The steps above, with a new certificate, work in every case.

On Kubernetes, digest mode needs nothing; it is the default. pgp mode needs the key as a file and its passphrase as a secret, both of which the chart mounts for you:

# values.yaml
config:
  signing:
    enabled: true
    mode: pgp
    key_path: /etc/ferroehr/signing-key.asc
  files:
    signing-key.asc: |
      -----BEGIN PGP PRIVATE KEY BLOCK-----
      …
secrets:
  signingKeyPassphrase: "…"

Every config.files key becomes /etc/ferroehr/<key>, mounted read-only from a chart Secret at mode 0440, and that volume holds the private key, so it is never world-readable inside the container. To go back to digest, set mode: digest and drop the key material; versions already signed keep their signatures and still verify.
