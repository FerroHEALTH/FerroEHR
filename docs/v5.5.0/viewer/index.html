FerroEHR Documentation

FerroEHR Viewer

ferroehr-viewer is a standalone web UI for managing an ITS-REST-1.1.0 CDR, this server or any other. It is a pure REST client: everything it does goes through the CDR’s public API (never the database), so what you see in the viewer is exactly what the API serves. The whole application is Rust (Leptos, drawn on the server and hydrated in the browser, which then draws each page after the first itself) on FerroUI, the component library the FerroHEALTH consoles share; there is no hand-written JavaScript anywhere, including its browser tests.

Running it

The quickstart compose ships the viewer as the ferroehr-viewer service on port 3000, behind the viewer profile, so it is opt-in and does not start with a plain docker compose up:

docker compose --profile viewer up
# → http://localhost:3000  (log in with the quickstart user ferroehr/ferroehr)

Standalone, point it at any CDR:

docker run -p 3000:3000 \
  -e FERROEHR_VIEWER__CDR__BASE_URL=https://cdr.example.org \
  ghcr.io/ferrohealth/ferroehr-viewer

On Kubernetes

The Helm chart deploys the viewer as its own Deployment, Service and ServiceAccount, with an optional Ingress and a NetworkPolicy that confines its egress to the CDR and DNS: the viewer is a REST client of the CDR by mandate, so the chart enforces that rather than trusting it. Off by default, and off renders nothing:

# values.yaml
viewer:
  enabled: true
  ingress:
    enabled: true
    hosts:
      - host: viewer.example.org
        paths:
          - path: /
            pathType: Prefix
  auth:
    oidc:
      enabled: true
      issuer: https://keycloak.example/realms/ferroehr
      clientId: ferroehr-viewer
      publicBaseUrl: https://viewer.example.org
  # the OIDC client secret is MOUNTED from a Secret you create, never env-borne
  existingSecret: viewer-oidc

It needs no database credential and never reaches the database. Before you enable OIDC: a registered client whose redirect URI matches publicBaseUrl, and a Secret holding its client secret. To turn the viewer off, set viewer.enabled: false and upgrade; every viewer object is removed and the CDR is untouched.

Note

To scale the viewer past one replica, set the same session.secret on every replica: the session is a sealed cookie any key-holding replica can serve. Without a configured secret each replica seals with its own ephemeral key, and visitors get signed out whenever a request lands on another pod.

Signing in

The sign-in page offers exactly the methods that can actually work: the viewer’s configured login modes intersected with the authentication schemes the CDR advertises (its WWW-Authenticate challenge). A Basic form is never shown against a bearer-only CDR, and vice versa. If the CDR cannot be reached at all, the page falls back to the viewer’s own configuration and renders anyway, and the outage then surfaces on the login attempt instead of hiding the page. A username or password the CDR refuses brings you back to the sign-in card with the refusal under the password.

The viewer verifies the CDR and the OIDC issuer against the platform trust store and the extra certificate authorities its configuration names: a CDR or an identity provider whose certificate comes from a private CA is trusted once cdr.tls.trust_roots_file or auth.oidc.tls.trust_roots_file names a PEM bundle holding that CA, on Linux and macOS alike. A file that cannot be read, or holds no certificate, refuses the start.

The viewer manages no accounts of its own: it authenticates you against the CDR (Basic) or your identity provider (OIDC), and there are no user, role, or password screens to find; those live in the CDR’s configuration and in your IdP.

The button with your name at the end of the top bar opens the user menu: who is signed in and how, Your preferences, Your access, the theme, Keyboard shortcuts and Sign out.

Your access

Your access (/access) answers what may this session do, and who says so: the principal and how it signed in (a Basic session replays its CDR account and carries no SMART scopes; an OIDC session carries an access token whose scopes are listed), every scope on the session read as its parsed grant (the compartment, the resource family and id pattern, and which of create, read, update, delete and search it permits, with a broad access marker on a bare *; an identity or launch scope such as openid, profile or launch/patient reads as the request it makes), and a previewer: paste any scope or a whole claim, press Read it, and read the same rendering. A malformed scope says what the grammar expected. The user menu and Server’s SMART tab link here.

The reading parses with the same grammar the CDR’s SMART on openEHR enforcement reads, so the two cannot drift. Scopes narrow access and never grant it; the CDR remains the enforcer.

When your session ends

A session ends when you sign out, when its idle window (session.idle_minutes) passes with no request from your browser, or when the CDR stops accepting the credential behind it (an expired or revoked token). Every page is drawn on the server, so the next page you ask for is where the viewer notices: it answers with the sign-in page, which says the session ended, and signing in again (Basic or OIDC) returns you to the page you asked for.

The idle window slides on each request your browser makes. The viewer polls nothing in the background, so a tab left open and untouched idles out after session.idle_minutes like a closed one, and the page it shows stays as it was drawn until you ask for another.

The deployment profile

The status pill at the end of the top bar says whether the CDR answers. A deployment that declares the sandbox profile (deployment_profile in its configuration, reported on GET /rest/status) raises a band under the top bar on every signed-in page: this deployment must not hold real patient data, with the number of production separations the server reported as open (a shared database credential, a shared cluster, no subject pseudonym namespace, no durable audit trail, schema preparation on the runtime credential). Its Details opens Server’s Overview, which names each one. A production deployment raises no band. The quickstart and the composed stacks run as sandbox; a CDR older than the profile reports none and the viewer claims nothing. See the deployment profile in the server configuration.

Configuration

One TOML file (ferroehr-viewer.toml, read from the path --config or FERROEHR_VIEWER_CONFIG names; with none named, no file is read), with FERROEHR_VIEWER__<SECTION>__<KEY> environment overrides and --set key=value pairs over both. Unknown keys and unknown FERROEHR_VIEWER_ variables are refused at startup. The CDR refuses only an unknown FERROEHR__ override, because the viewer’s variables share its prefix:

Commands

ferroehr-viewer (or ferroehr-viewer serve) serves until SIGTERM or SIGINT. ferroehr-viewer config check reads the configuration and builds the CDR and issuer clients, reading every TLS file, without reaching either. ferroehr-viewer healthcheck, the image’s HEALTHCHECK, asks the viewer beside it for GET /health/readiness over the loopback (over TLS when server.tls is set) and exits 0 only on 200. The viewer serves the family’s health routes: /health/liveness, /health/readiness and /health.

Browser security headers

Every response carries a Content-Security-Policy whose script source is a nonce minted for that response alone, with 'wasm-unsafe-eval' for the WebAssembly and neither 'unsafe-inline' nor 'unsafe-eval', beside X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer and Cross-Origin-Opener-Policy: same-origin. Every document is Cache-Control: no-store; the content-hashed bundle under /pkg/ is no-cache, so a browser revalidates it. A request that is not a safe method (a form post, a server function call) is refused 403 unless the browser’s Sec-Fetch-Site says it came from the viewer’s own pages; without that header its Origin or Referer must name auth.oidc.public_base_url.

The viewer is stateless: it has no database and keeps no local files of its own. Everything it shows, including how stored queries are grouped, which is derived from the namespace in each query’s qualified name, lives in the CDR and is read over ITS-REST, so nothing here needs backing up and every replica shows the same repository. Sessions are a sealed cookie (AES-256-GCM, keyed by session.secret), so any replica holding the key can serve any signed-in visitor.

Login and sessions live in the viewer’s server; the browser stores only the encrypted session cookie: CDR credentials and bearer tokens never reach it in readable form.

How the pages work

The viewer draws every page on its server and sends it complete. Every link is a link and every action is a form that posts to the page it sits on, so the whole viewer works with JavaScript off. The browser then loads a small WebAssembly bundle that adds behaviour to a few parts of a page (the code editor, the path trees, the chart legend, the date pickers, the user menu’s keyboard handling, the subject reveal and Copy buttons); nothing on a page waits for it. There is no hand-written JavaScript.

An editor (a new EHR, a composition, the EHR status, the directory, a party, a subscription, a template upload) ends in a bar docked at the foot of the page: what has changed, Discard, and the save. A save that the CDR refuses keeps what you typed on the page beside the CDR’s own words.

The screens are listed in the sidebar; below 48 rem it folds into a drawer behind the menu button.

  • Dashboard: record counts, the compositions committed per day, and the stored queries by namespace. See Queries.
  • EHRs: find, create and delete EHRs; each EHR’s compositions, directory, status, contributions and tags. See Templates and EHRs.
  • Parties: the demographic parties, their versions, relationships and tags. See Parties.
  • Templates: upload and read ADL 1.4 and ADL 2 operational templates. See Templates and EHRs.
  • Terminology: the terminologies the CDR serves. See Terminology.
  • Stored queries and Query: build or write AQL, run it, chart and export the rows, save it to the CDR. See Queries.
  • Server: what the CDR is, how it runs and what it serves, and the Audit log. See Server and audit log.
  • Subscriptions: the CDR’s event subscriptions. See Event subscriptions.
  • Configuration: the CDR’s redacted running configuration, by section.
  • About: the viewer, the CDR and their versions, the manufacturer and the CDR’s conformance manifest.

The top bar’s search takes an EHR id, a composition or party uid, a subject id, a template id or a stored-query name. From the second character a panel under the field shows what matches, five of a kind; the arrow keys move through it, Enter opens a hit and Escape closes it. Submitting the search opens the find page, which lists every match, or the other ways to find a record when nothing does.

The footer under every page names the viewer and its version, the manufacturer (Cadasto B.V.), and an About link.

Paging

A listing that can show patient data (the EHRs, an EHR’s compositions and contributions, the audit log) pages with First, Previous, Next and Last under the table and keeps its page in a cookie for the browser session, never in the address or the history, as FerroUI asks of every family console. A filter stays in the address, so a filtered view is still shareable; the page you were on is not. Each step is a form that posts to /paging and comes back to the listing, so paging works with JavaScript off.

Preferences and the keyboard

Your preferences keeps the viewer’s display choices, each in its own cookie for that browser: the theme, the reading choices, and the keyboard shortcuts. See Preferences and the theme.
