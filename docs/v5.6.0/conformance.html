FerroEHR Documentation

Conformance

FerroEHR makes a measured claim: it is an openEHR-spec-conformant Clinical Data Repository, and that claim is backed by a test run you can reproduce. This chapter explains what conformance means here, how to run the suite against FerroEHR, and how to read the artefacts it produces.

What is measured

Conformance is checked by Veredictum, a separate CNF 2.0 reference runner. It lives in its own repository, has the same maintainer as FerroEHR, and is consumed here at a pinned version. Its catalogue is a set of Arazzo workflows, one document per behaviour, grouped in capability folders. Every workflow cites the specification sentence its expectation rests on, quoted from the vendored openEHR text. Where the release leaves a behaviour to the implementation, the catalogue names an option with its arms and the sentence that leaves it open, and the party statement selects one arm. Where the release is silent or contradicts itself, no workflow asserts the behaviour, and the citation names the outbound report instead: a specification silence is never resolved privately. Every expectation traces to specification text, never to any server’s observed behaviour. The catalogue groups its folders into chapters:

ChapterScope
EHREHR, EHR_STATUS, COMPOSITION, DIRECTORY, CONTRIBUTION and item tags
DefinitionsADL 1.4 and ADL 2 templates and stored queries
QueryAQL query execution with committed result-set grounds
DemographicParties and their versions
Content validationReference-Model and archetype-constraint accept and reject tables
Simplified formatsFLAT and STRUCTURED commit and read
AdminThe administrative delete operations
Security and privacyAuthenticated access and authorization separation
SMART on openEHRSMART App Launch discovery and resource-scope enforcement
SystemThe OPTIONS capability and conformance manifest

A run judges every row of every case and counts it in one of two parts. BASE holds what every server that claims a capability must do. OPTIONS holds the cases of an option the specification leaves to the implementation, where the party statement selects one arm, and the cases that rest on TRIAL text. A row of an arm FerroEHR did not select is skipped with the citation that makes it not apply, so a skipped row is never a silent pass.

Each row ends in one of five outcomes. A failed row counts against the server. A warning row is a SHOULD the server did not follow and never counts against it. An errored row could not be judged: it counts against the server unless its record names the instrument as the cause. A skipped row was not run, and names its reason. A released run also skips every case that rests on development text alone (development-only), and a development run skips every case whose cited text the development snapshot drops or contradicts (cited-text-absent, contested-in-development).

Note

The runner publishes a JSON Schema for every artefact family it writes, so a consumer can validate a record without trusting the tool that produced it. The instrument is built from the currently pinned specifications (AQL 1.1.0, Terminology 3.1.0, ITS-REST 1.1.0, and the Reference Model generation the system under test runs: for FerroEHR’s development run the default development profile, RM 1.2.0, and for its released run the stable profile; the composed stack takes the profile from configuration, so a stable-profile run is the same catalogue against the released generation).

The party set

The runner is a separate project with its own release line, so the instrument and the system it judges do not share a build. It assesses any openEHR CDR reachable over HTTP; this repository runs it against FerroEHR alone. What it reads about FerroEHR is the party set under docs/conformance/party/ferroehr/:

  • statement.json claims the capability folders of the catalogue FerroEHR serves and selects one arm of every option the catalogue leaves to the implementation (canonical XML on each resource, the Simplified Formats, version signing, the administrative delete, and the others). Each arm states what the server does, and veredictum validate --statement holds the file to the published statement schema and the catalogue before a run.
  • ixit.json describes the deployment: the system_id the server stamps into commit audits and the version ids it mints, the environment a measured run happened on, and exclusive_server, which lets the workflows that delete every EHR run.

Credentials are in neither file. The run reads them from the environment.

Running the suite yourself

The suite runs against a real, deployed server (the same container image and stack a deployment uses), so the wire under test is always the production artefact. From a checkout with Docker or Podman available:

bash scripts/conformance.sh

The script reviews the statement, composes one FerroEHR deployment from the current sources on fresh volumes, runs veredictum test through the pinned release image with the Basic users of docker/ferroehr.dev.toml and the SMART Platform base URL, writes results.json, recording.har and the JUnit, CTRF and Markdown views export renders to docs/conformance/ferroehr/, and tears the stack down. The recording holds the server’s response bodies, so it is never committed.

CONF_PROFILE picks the specification text the case citations are read against. released, the default, is the frozen openEHR release: it is the record and alone backs a released claim. development is the pinned master of each openEHR repository, the text FerroEHR builds on (RM 1.2.0, BASE 1.3.0); its views go to docs/conformance/ferroehr-development/ and are never mixed into the record.

Useful knobs: CONF_DOCUMENTS to narrow the run to named documents (a working tool, never the record), CONF_OUT for a different artefact root, CONF_NO_COMPOSE with CONF_BASE_URL to run against an already-deployed FerroEHR, SKIP_BUILD to compose a published image instead of building from source, and CONTAINER_ENGINE to choose between Docker and Podman.

The script also takes one stage: review runs veredictum validate --statement alone, up composes the deployment and leaves it serving, and down removes it with its volumes. The Conformance workflow uses these stages to run the same deployment in CI. It compiles no server of its own: it judges the server another lane built for the commit, runs up, and drives the catalogue through the Veredictum GitHub Action, pinned by commit SHA, on the same release image by digest, twice: once under the released profile and once, on fresh volumes, under the development profile. Both runs include the SMART documents. The released run decides the job: it fails on a failed or errored row there. Each run’s Markdown summary goes on the job summary under its own heading, and each profile’s results, JUnit and CTRF views are kept as an artifact of their own.

The posture a run covers

The one deployment runs the SMART resource-server role with a trusted test issuer, digest version signing, and FerroTERM as its terminology server, in the fail-open posture.

  • SMART is part of the posture. The tokens the SMART documents present are signed by a committed test issuer: public test key material for the harness, never usable for anything else.
  • External terminology is part of the posture too. An archetype can constrain a coded element to a value set only an external terminology query server can resolve, so the pipeline composes a real FHIR R4B server beside the CDR, seeded with synthetic test code systems and value sets. That covers AQL TERMINOLOGY() resolved through the routed server, and commit-time validation of a bound value set. What a deployment does when the value set cannot be resolved at all is not decided by any openEHR text, so it is a declared option arm rather than a verdict.

A measured performance run (scripts/conformance.sh perf) changes two things, both in docker/sut-measurement.yml: rate limiting is off, because the scout ramp offers load past the server’s knee and a throttled request would measure the limiter instead of the server, and response compression is off, because the posture the run declares has it off. veredictum perf writes no record if the server answered any 429, so a measurement can never be silently limiter-shaped.

Reading the artefacts

A run writes results.json and three views veredictum export renders from it: junit.xml, ctrf.json and summary.md. Each view is a pure function of results.json, so the same results give the same bytes.

  • results.json is the record: the instrument and its version, the specification profile, the server’s own OPTIONS answer, an outline of every case with its chapter, band and part, and one row per workflow row with its outcome, its inputs and, for a skipped row, the reason and the citation.
  • summary.md is the view for a person: the counts per part, then chapter by chapter, with each red row opened up to the step, what was checked, expected against received, and the cited sentence.
  • junit.xml and ctrf.json are the views a CI system shows. The Conformance workflow keeps them as run artifacts and does not commit them.

results.json and summary.md of one released-profile run are committed under docs/conformance/ferroehr/. The website and this page read their numbers from that record at build time, and the build fails when summary.md and results.json disagree.

What conformance does not cover

The catalogue measures the openEHR platform surface, including the simplified (FLAT/STRUCTURED) formats chapter of the ITS-REST specification. It deliberately does not stand in for a performance benchmark: durations recorded during the functional run are telemetry only, and the measured performance record owns that claim (Performance).

The other honest boundary is the gap between openEHR’s service model and its released REST wire. Several service operations were never surfaced as endpoints (listing an EHR’s contributions, counting stored templates or queries, deleting a template or a stored query) so a case that addresses one has no wire to drive on this technology profile. FerroEHR does serve routes of its own design for several of them (see Admin & messaging APIs and the archetype routes in Templates & validation).
