[auth]

Authentication: bearer tokens of one or more trusted issuers, Basic credentials, or both. [auth] is the section every FerroHEALTH product shares, checked by the ferrohealth-smart crate (0.9). FerroEHR is a resource server: it checks tokens and never issues them. Every person a request comes from is bound to a demographic PERSON (see [authz.party_binding]).

[auth]
enabled = true

[[auth.issuer]]
issuer = "https://keycloak.example.com/realms/staff"
kind = "persons"
profile = "keycloak"
audience = ["ferroehr"]
first_party_clients = ["ferroehr-viewer"]

[[auth.party]]
issuer = "https://keycloak.example.com/realms/staff"
identifier_issuer = "urn:example:staff-login"
identifier_type = "uuid"

[[auth.basic.users]]
user = "clinician"
password_hash = "$argon2id$v=19$m=19456,t=2,p=1$…$…"   # never a plaintext password
scopes = ["user/composition-*.cruds", "user/template-*.cruds", "user/aql-*.cruds"]

[[auth.issuer]]: the trusted issuers

Each issuer’s metadata is read at boot, at the RFC 8414 §3 location first and the OpenID Connect Discovery 1.0 §4 location after a 404, and with it the key set at its jwks_uri, so an authorization server that cannot be reached refuses the start. Every setting of an issuer lives on its own table. No two issuers of one node share an audience, so one audience is one issuer and one token form; the node’s audience must also differ from every other node’s, an operator rule boot cannot see.

Warning

auth.enabled = true with no mechanism is a boot error. Such a server could only refuse every request while advertising an authentication scheme it does not implement, which RFC 9110 §11.6.1 forbids: a 401 challenge must name a scheme applicable to the target resource. Configure an issuer, configure [[auth.basic.users]], or set auth.enabled = false for a development server.

The key-set fetches verify the identity provider’s certificate against the platform trust store and follow no redirects. An identity provider whose certificate comes from a private CA is trusted once that CA is in the image’s system store or in a directory or file named by SSL_CERT_DIR or SSL_CERT_FILE. A key set that cannot be read when a token needs it answers 503, never 401: the server cannot decide, and a 401 would tell a caller with a valid token that its credential was refused.

A validated token must also carry a non-blank sub claim: the authenticated subject is stamped into the audit trail, so a token without one is refused with 401 rather than recorded under a placeholder identity. A bearer token outside the RFC 6750 §2.1 b64token alphabet is refused the same way, with 401 and error="invalid_token".

Opaque tokens by introspection

An authorization server that issues opaque access tokens is served with mode = "introspection" on its [[auth.issuer]] table, whose [auth.issuer.introspection] table holds the keys below. Each bearer token is posted to the issuer’s introspection endpoint (RFC 7662 §2.1), and the active response stands in for the JWT claims: sub, scope, the roles of role_claims, aud against audience and iss against the issuer. An inactive token is a 401. An endpoint that cannot answer is a 503, because the server cannot decide. An active response is reused until its exp, at most cache_max_age.

The Basic-auth user store

[[auth.basic.users]] is an array of tables. A Basic user is always a person: it maps to the PERSON carrying its binding key through [[authz.party_binding.basic_user]], and a Basic user with no mapping refuses the start, naming the user. A machine authenticates with the client credentials grant (RFC 6749 §4.4), and a system/ scope on a Basic user refuses the start.

KeyTypeDefaultDescription
userstringrequiredThe user-id. Empty, or with a colon or a control character, is a boot error (RFC 7617 §2).
password_hashsecretrequiredArgon2id PHC hash ($argon2id$v=19$…), never a plaintext password. Boot-validated against the OWASP floor; see below.
password_hash_filepathunsetRead the hash from a file instead, for a mounted secret. A hash is an offline cracking target, so prefer this wherever the configuration file itself is not treated as sensitive. Exactly one of the pair is required.
scopeslist of string[]The SMART on openEHR scopes the user holds, checked on every route exactly like a token’s scope claim. A user with none is refused everywhere a requirement applies.
roleslist of string[]The user’s RBAC roles, upper-cased on authentication. A user with none holds no role and is refused wherever [authz.rbac] asks for one.

[auth.basic] itself takes one key beside the users:

KeyTypeDefaultDescription
cache_ttlduration"5min"How long a credential that verified is kept, so a repeat request skips the Argon2id derivation; "0s" turns the cache off and checks every request. The entry is named by a keyed hash of user-id:password under a key drawn at boot, never the password, and only a credential that verified is kept, so a wrong password always pays the derivation. The cache holds at most 4096 credentials and empties at a restart. The TTL bounds how long a removed user keeps working, which matters only until the restart that applies the new user list. Argon2id is slow by design, so with the cache off its cost bounds how many Basic requests a core can answer.

Warning

Every password_hash must meet the OWASP Argon2id floor: m>=19456 (19 MiB), t>=2, p>=1, algorithm argon2id. Anything weaker (or a non-argon2id PHC string, or an unparsable one) is a boot error naming the user. This is checked at startup because the verifier takes its cost parameters from the stored hash, so a deliberately cheap hash would otherwise verify happily and silently weaken every password in the store. The floor is the OWASP Password Storage Cheat Sheet §Argon2id minimum.

An unknown user-id is checked against a decoy hash of the same cost, so the time a refusal takes does not say whether the user exists.

The party mapping

SCIM provisioning, just-in-time creation and the login binding read and write the same demographic parties under one mapping. It names the templates each party is valid against, the identifier selectors of the binding key, userName and externalId, and where each SCIM attribute and OpenID Connect claim goes. Names go in PARTY.identities and identifiers in PARTY.details (RM demographic §Names and Addresses, §Party Identification), and boot refuses a name mapped into details or an identifier mapped into identities. No openEHR specification governs this mapping: it is FerroEHR’s own design, and its targets are RM demographic paths.

With Microsoft Entra ID, map the object id to externalId (Entra’s matching) and to the binding-key attribute (the binding): two attributes, two selectors. The key’s [[auth.party]] identifier_type is guid, so a key differing only in case binds one login.

Boot refuses, naming the key: no or two default tables; a selector path that does not compile; two equal selectors; a key whose scheme [privacy.identifier_protection] protects; any selector under the Dutch BSN namespace (OID 2.16.840.1.113883.2.4.6.3); a key fed by an email address, a phone number, preferred_username, name, upn or unique_name; a template that is absent, rooted at another class or lacks a mapped path; a path whose type cannot carry its source; and a representation type with no subject_relationship code. Deleting a template the mapping names is refused with 409.

The parties the binding relies on are protected: a PERSON of a mapped template carrying a selector identifier, its professional ROLE, a representation relationship, and a GROUP of the group template. Only an administrator (authz.rbac.admin_role) writes one through the demographic API, including the creation of a party that carries a selector identifier. An administrator’s version that leaves a protected identifier out is refused with 422. A present binding key is immutable (RFC 7643 §2.2): a version that changes it is refused with 403, and POST /admin/party/binding-key is the one change. Each selector value binds one live party: a commit that gives a binding key, a userName (compared after RFC 8265 width mapping, lower case and NFC), an externalId or a group displayName a second party is refused with 409. A deleted PERSON leaves its key as a tombstone that refuses the login until an administrator binds the key again.

Changing the mapping

The side table is filled from the configured mapping and the party versions. The first boot fills it and stores the mapping’s digest; a replica whose mapping digest differs from the stored one refuses to start, naming both digests. Each running replica holds a lease it renews every 20 seconds. A mapping change is a stop-the-world step:

  1. Stop every replica. With Helm, scale the deployment to zero first: a rolling upgrade would start new replicas beside old ones.
  2. Run ferroehr party-binding refill with the new configuration. It refuses while a replica’s lease was renewed within the last minute, and refuses a store in which two parties carry one selector value, naming both.
  3. Start the replicas with the new mapping. A replica still holding the old mapping refuses to start.

How a login is looked up

Every request of a person is looked up in the binding side table of the party store, on the party database role, with no cache, so a change to a party takes effect on the next request on every instance. The table holds the binding key of each PERSON of a mapped template that performs a professional ROLE (a ROLE of the mapped role template that its roles list, that names it as performer, whose state is complete or incomplete and whose time_validity holds today’s date in UTC) or that is the source of a representation relationship. A key of type guid or uuid is compared in lower case. The table is written in each party commit’s transaction and can be rebuilt from the party versions alone.

The request is refused with 403 and the binding code in the problem body when the login matches two parties (refused-ambiguous), when its party is inactive (refused-inactive) or abandoned (refused-abandoned), when its key belongs to a deleted party (refused-deprovisioned), when the token carries no key claim (refused-key-claim-missing), when the party lacks the marker the caller’s kind needs (refused-wrong-marker), when the groups a token asserts cannot be read (refused-groups-unavailable), when a guest comes from an issuer whose table does not set guests (refused-guest), and when a representative’s token names a subject its party has no live representation relationship to (refused-representation-unrecorded). A party store or an identity provider that cannot answer is answered 503, with Retry-After when the identity provider gave one.

A person whose login matches no party is refused with 403 and refused-unbound on every request, reads and writes alike; only the public endpoints outside the auth layer answer. The problem names the identifier issuer to provision the person under, and the refusal of a token without the key claim names the missing claim instead. No setting serves an unbound person under a login-only committer, so provision every professional (through SCIM or the demographic API) before you add a persons issuer, or let the issuer create a provisional PERSON at the first login (just-in-time creation). Each refusal writes one warn line naming the issuer and the outcome, never the claim value, and counts into the binding_refusals metric by issuer and outcome.

A representative reaches only the EHR whose EHR_STATUS.subject.external_ref names the subject it represents: the issuer’s representation claim carries the subject’s party id, matched without regard to case, and the subject must be the target of one of the representative’s live relationships, so a representative of an issuer no [[auth.party]] table binds is refused. Every composition, EHR_STATUS, directory, contribution and query request is held to that EHR, whatever the token’s scopes cover; a query must name it with ehr_id. Templates stay readable. A persons token whose only clinical scopes are patient/ is a professional confined to its launch EHR, and its commits record the professional, never PARTY_SELF.

Just-in-time creation

Just-in-time creation lets a professional with no party work under their own account at their first login, before SCIM or an administrator completes the record. It is off by default and enabled per persons issuer in one [[authz.party_binding.issuer]] table. When a login of that issuer matches no party, FerroEHR commits one PERSON of the default template with lifecycle state 553|incomplete|, which RM common §Incomplete Content allows for “incomplete demographic details”, and its professional ROLE in the same demographic contribution, then serves the request bound to it. The next request binds to that PERSON and creates nothing. When a login creates a party is FerroEHR’s own design: no openEHR specification governs it.

What a provisional person may do is decided by their SMART scopes and roles, as for anyone. A SCIM client whose binding_issuer is the issuer’s identifier_issuer completes the PERSON: it finds it by userName, with a binding key equal to its own, writes the externalId with a PATCH, and a complete PUT completes it. SCIM active = false abandons it.

Because the data come from the identity provider and not from the person, tell the professionals what Art. 14 asks: what is copied, from which source, and why. On a realm or tenant that creates persons, make the name attributes administrator-controlled, as the key is; Enterprise identity providers shows the settings per identity provider.

Users

A User is a PERSON of the default person template performing the professional ROLE. The client serves these operations (RFC 7644 §3):

  • POST /scim/v2/Users creates the PERSON and its ROLE in one demographic CONTRIBUTION, under the client as committer, and answers 201 with the User, its Location and its ETag. The body carries userName and the binding key in loginIdentifier; externalId and every mapped attribute are optional. A version that fits its template in full is complete, and one that fits only with every lower limit at zero is incomplete, which the User’s lifecycleState and missingPaths name. A User created with active = false is 400 invalidValue.
  • GET /scim/v2/Users/{id} answers the User with its ETag, the weak tag of its version, and 304 to an If-None-Match naming that version.
  • GET /scim/v2/Users answers a ListResponse, an empty one with 200 when nothing matches. filter takes eq and and over userName, externalId and id; names and operators are compared in any case, and anything else is 400 invalidFilter. startIndex and count page the result, at most max_results at a time.

The User’s userName, externalId and binding key are DV_IDENTIFIERs at their selectors, issued by the client’s binding_issuer. A client sees only its own Users, the ones whose key its binding_issuer issues: every other id is 404 and absent from every list, as is a PERSON without a live professional ROLE. The userName index spans every client, so a 409 uniqueness tells one client that a userName exists under another; externalId is unique within one client. Every SCIM request is an access record of the client, with the PERSON as its object.

A User is changed and removed through these operations:

  • PUT /scim/v2/Users/{id} replaces the User (RFC 7644 §3.5.1). A mapped attribute the body leaves out is cleared; the binding key and externalId are kept, and a left-out active keeps the lifecycle state.
  • PATCH /scim/v2/Users/{id} applies the RFC 7644 §3.5.2 operations, value paths and a replace without path included, and commits the result as one version. The operation is read in any case, as the Entra ID client sends Replace.
  • DELETE /scim/v2/Users/{id} logically deletes the PERSON and its professional ROLE in one demographic CONTRIBUTION and answers 204. Every later request on the id is 404, the User leaves every list, and a new User may take its userName. The binding key stays behind as a tombstone: a login on it is refused as deprovisioned until the owning client creates a User with it again.

Each write answers with the User and its new ETag. An If-Match naming another version is 412, a changed binding key is 400 mutability, and a write without If-Match is accepted (RFC 7644 §3.14 makes entity tags a MAY). active drives the lifecycle state of the PERSON (RM common §Version Lifecycle):

The versions of a deleted User are kept for the record-keeping duties that need the professional’s identification (GDPR Art. 6(1)(c), laid down in law as Art. 6(3) requires: in the Netherlands BW 7:454(3), twenty years, and the logging duty of the Besluit elektronische gegevensverwerking door zorgaanbieders). Outside the Netherlands, name your national retention provision. Enable the identity provider’s protection against accidental deletions beside max_deactivations.

Only the attribution minimum waits for that horizon: the name, the binding key and the identifiers, userName and externalId among them. The contacts serve no attribution, so FerroEHR erases them (GDPR Art. 5(1)(e)): with auth.scim.contact_erasure_delay = 0 the deletion removes the contacts of every version of the PERSON in the same transaction, and with a period a sweep that runs every minute removes them once the period has passed. The sweep reaches every deleted PERSON whose binding key a [[auth.scim.client]] issues, an administrator’s demographic DELETE included. Each version keeps its uid, audit and contribution, and its node rows are derived again from the erased body. A server signature on such a version is removed, because it was taken over the content the erasure changed. Each erasure is an access record, a delete of party:<id>#contacts. A login on the key is still refused as deprovisioned.

Groups

When [authz.party_binding.group] names a display_name and [authz.party_binding.membership] is set, /scim/v2/Groups is served beside /Users, and /scim/v2/ResourceTypes lists the Group. A Group is a demographic GROUP of the group template:

  • its displayName is the GROUP’s PARTY_IDENTITY, unique across the live Groups after case folding, so a duplicate is 409 uniqueness;
  • its externalId is a DV_IDENTIFIER at the external_id selector under the group_identifier_issuer of the [[auth.party]] table whose identifier_issuer is the client’s binding_issuer, so the group claim of that issuer’s tokens matches it. ferroehr config check refuses a client whose table sets no group_identifier_issuer;
  • each member holds one inline PARTY_RELATIONSHIP of the membership archetype, with its PERSON as source and the GROUP as target, stored in the member’s own version (RM demographic §Party Relationships). No ROLE is created for a Group, and a PERSON in no Group has relationships Void.

A Group belongs to the client that created it; every other client gets 404. A member is a User of the same client: a member naming another client’s User, an unknown id or a Group (nested Groups are not supported) is 400 invalidValue. What a Group allows stays with the token’s scopes and roles; the access record lists the Groups the token names that the person belongs to, and a Group in inactive or abandoned lists no member.

  • POST /scim/v2/Groups creates the GROUP with its members, if any, and answers 201 with the Group, its Location and ETag.
  • GET /scim/v2/Groups/{id} and GET /scim/v2/Groups filter with eq and and over displayName, externalId and id, and excludedAttributes=members leaves the members out. Each member is served with its value, $ref and type.
  • PATCH /scim/v2/Groups/{id} answers 204 with the new ETag (RFC 7644 §3.5.2). add of members adds the listed members; remove with the filter members[value eq "<id>"] removes that member, and remove of members with neither a filter nor a value list removes them all.
  • PUT /scim/v2/Groups/{id} replaces the displayName and the members, keeps a left-out externalId, and answers 200 with the Group.
  • DELETE /scim/v2/Groups/{id} logically deletes the GROUP with its memberships, and every later request on the id is 404.

Entra compatibility deviation. A remove of members that carries a value list removes only the listed members, the request Microsoft Entra ID sends. RFC 7644 §3.5.2.2 removes “the attribute and all values” when no filter is specified; FerroEHR follows Entra only when the value list is present.

A membership change is a new version of each member’s PERSON it touches, in one CONTRIBUTION, and the GROUP gets no version; a change costs the same whatever the Group’s size. The Group’s ETag is its GROUP version with a membership revision that moves with every membership change, so it changes whenever its members do (RFC 7644 §3.14). The member User’s ETag changes too, since its PERSON holds the membership (RFC 7643 §4.1.2); its body does not, because the User serves no groups attribute. Deleting a User deletes the memberships its PERSON holds with it. Deleting a Group drops the membership of each active member in the CONTRIBUTION that deletes the GROUP. A GROUP an administrator set inactive or abandoned keeps its version, since the version lifecycle draws no update of either state, and a SCIM write to such a Group is 400 invalidValue.

Deactivated Users leave their Groups. The version lifecycle draws no update of an inactive or abandoned PERSON (RM common master06 §Version Lifecycle), so such a PERSON cannot take a membership change, and an inactive PERSON binds to nothing. Setting a User’s active to false therefore drops all its memberships in the same version, and each Group’s ETag changes. Microsoft Entra ID often disables a user and then removes it from its groups; the later remove finds nothing to remove and answers 204. An add naming an inactive or abandoned User is 400 invalidValue (“reactivate the User first”). A reactivated User belongs to no Group until its client adds it again.

Provision from Microsoft Entra ID

Microsoft Entra ID provisions through a non-gallery enterprise application. FerroEHR validates the access token your own authorization server issues to it, so the steps split between the two.

  1. Map the person template. Give the default [[authz.party_binding.person.template]] a user_name and an external_id selector, and map the attributes Entra sends, for example:

    [[authz.party_binding.person.attribute]]
scim = "name.formatted"
name = true
path = { "FerroEHR professional" = "/identities[at0002]/details[at0003]/items[at0004]" }

[[authz.party_binding.person.attribute]]
scim = 'emails[type eq "work"].value'
path = { "FerroEHR professional" = "/contacts[at0005]/addresses[at0006]/details[at0007]/items[at0008]" }

    A value path such as emails[type eq "work"].value serves the value and its type. FerroEHR holds one value per type and no preference among them, so /scim/v2/Schemas declares primary read-only and the primary Entra sends is ignored (RFC 7644 §3.3).

  2. Declare the client. Add a [[auth.scim.client]] whose issuer is your authorization server, an [[auth.issuer]] of kind machines, and whose binding_issuer is the identifier_issuer of the [[auth.party]] your professionals log in through. Set public_base_url to the origin Entra reaches. In the Helm chart, config.the [auth.scim] table: true also adds the /scim/v2 path to the Ingress. ferroehr config check refuses a mapping the endpoint cannot serve.

  3. Federate Entra’s credential at your authorization server. Entra’s Workload Identity Federation presents a signed assertion, which your authorization server exchanges for a client-credentials access token (RFC 7523 §2.2). These checks are your authorization server’s, not FerroEHR’s, so verify each one there, as Microsoft’s “Workload Identity Federation for SCIM Provisioning” guide requires:

    • iss is pinned to your full tenant issuer, https://login.microsoftonline.com/<tenant>/v2.0, and the assertion verifies against that tenant’s key set.
    • aud is pinned to api://<workload-identity-app-id>, with one workload-identity application per FerroEHR deployment.
    • azp is pinned to the application id of Microsoft’s provisioning service.
    • uti is cached for the lifetime of the assertion, and an assertion whose uti was seen before is refused as a replay.
    • The access token it issues holds the client’s scope, names the client in client_id, and lives between 1 and 6 hours, the range Microsoft’s guide asks for.

    The assertion’s sub is the object id of a Microsoft application that every integration in the tenant shares, never your client_id, so it does not meet RFC 7523 §3 item 2.B. Accepting it is a deviation of your authorization server; record it there. Leaving Entra’s Secret Token blank, so that Entra uses its own token, is not supported: Microsoft reserves it for testing, and every non-gallery application in the tenant receives a token with the same iss and aud (RFC 9700 §2.3). A long-lived bearer token is not supported either.

  4. Point Entra at FerroEHR. Set the Tenant URL to <public_base_url>/scim/v2 and run Test Connection. Entra queries /Users with filter=externalId eq "<random guid>", which FerroEHR answers with an empty ListResponse, and fetches a random User and a random Group, each answered 404.

  5. Map the attributes in Entra. Map userName, externalId, active and the attributes of step 1. Map the attribute that carries the professional’s login identifier to urn:ietf:params:scim:schemas:extension:ferrohealth:2.0:User:loginIdentifier; Entra sends it without listing the extension in schemas, which FerroEHR accepts. An attribute the person template does not map is refused as undefined, so remove the rest of Entra’s default mappings.

  6. Protect against mass deactivation. Turn on Entra’s accidental deletions prevention, with a threshold at or below max_deactivations.

  7. Provision groups. Map the group’s objectId to its externalId, so the object ids Entra puts in the groups claim match, and provision only the groups assigned to the application, which keeps a person’s token under the groups overage limit. Entra creates each Group with no member, reads it with excludedAttributes=members, finds it by displayName, and adds and removes members with PATCH.

Entra writes Replace and Add with a capital letter, disables a User with active = false, sends DELETE once the user is removed, and never sends a null. A value cleared in Entra therefore stays in FerroEHR until the User is replaced or deleted, or an administrator removes it.

Note

verify_on_read resolves to strict when signing is enabled. On every read the server recomputes the signature of a version it signed and, on a mismatch, returns a 500 integrity fault rather than silently serving a provably corrupt record. Set it explicitly to warn (log + meter version_signature_invalid_total, still serve) or off (never check). Client-supplied signatures (an author’s own, or one carried by an imported version) are always stored verbatim and never re-verified, whatever this setting says, because the author may have signed a different agreed serialization.

Warning

pgp mode fails closed at boot if the key is missing or unusable: the server will not start. Verify the key and passphrase before switching modes.

Choose an Ed25519 signing key

The server refuses an ECDSA (P-256, P-384, P-521, secp256k1, Brainpool) or Ed448 signing key at boot: their private-key arithmetic runs on crypto-bigint 0.5, whose constant-time operations can branch on secret values (RUSTSEC-2026-0387), with no fixed release on that line. The boot error names the advisory. Move to Ed25519 with the steps below; the old certificate goes in retired_key_files, where it keeps verifying, because verification uses only public values.

An RSA signing key is accepted, but it makes every commit perform an RSA private-key operation, the operation the Marvin timing sidechannel concerns (RUSTSEC-2023-0071 / CVE-2023-49092), for which the underlying rsa crate has no fixed release. An Ed25519 key keeps that code off the signing path entirely.

The server does not refuse an RSA key: a repository whose history is already RSA-signed needs that key to keep verifying, and signatures are immutable committed facts that cannot be re-issued. Instead it logs a warning at boot naming the advisory. To clear it:

  1. Generate a new signing key: gpg --quick-generate-key "…" ed25519 sign, and export the armored secret key to key_file.
  2. Export the public half of the old certificate and add it to retired_key_files, so versions signed with it still verify (see above).
  3. Restart. New versions are signed with Ed25519; old ones keep verifying.

Rotation inside one certificate is cheaper still: add an Ed25519 signing subkey to the existing certificate, export the armored secret key again to key_file, and restart. The server signs with the newest subkey whose binding grants signing and that is neither expired nor revoked (the rule), with no retired_key_files entry needed: the certificate keeps the previous subkey, so past signatures continue to verify. For a refused ECDSA or Ed448 key this works when the new Ed25519 subkey is the one chosen. The steps above, with a new certificate, work in every case.

On Kubernetes, digest mode needs nothing; it is the default. pgp mode needs the key as a file and its passphrase as a secret, both of which the chart mounts for you:

# values.yaml
config:
  signing:
    enabled: true
    mode: pgp
    key_file: /etc/ferroehr/signing-key.asc
  files:
    signing-key.asc: |
      -----BEGIN PGP PRIVATE KEY BLOCK-----
      …
secrets:
  signingKeyPassphrase: "…"

Every config.files key becomes /etc/ferroehr/<key>, mounted read-only from a chart Secret at mode 0440, and that volume holds the private key, so it is never world-readable inside the container. To go back to digest, set mode: digest and drop the key material; versions already signed keep their signatures and still verify.

[record.versioning]

What a commit stores is not a setting: a version whose content equals the current version’s is committed like any other, with its own commit audit, contribution, version id and ETag, and the content is stored once (the new version reads its predecessor’s node rows). The one setting here is the answer to a repeated send of the same content.

KeyTypeDefaultDescription
record.versioning.idempotent_resendboolfalseWhen true, a PUT whose content equals the current version’s commits nothing and answers like a successful update with the existing version: 200 (or 204 under Prefer: return=minimal), and that version’s ETag and Location.

Turn it on only for the integration that needs it: with the rule on, the repeated send leaves no commit audit and no contribution, so the version history does not record that the content was confirmed again, where the default records every committal as the RM asks (RM common master06 §Committal and Audits). What the repeated send does leave is one record on the access log ([audit]), operation resend, naming the version the content matched and its content digest (<version uid>#sha256:<digest>), the committer and the time: the entry Cadasto writes for a skipped send, which says the last version was saved one more time. The content is matched against the current version only, the one If-Match names; content equal to an earlier version’s is committed as a new version. The openEHR REST API does not govern skipping an identical commit; the answer is FerroEHR’s own, chosen to match what a client sees from Cadasto.
