A pure-Rust openEHR Clinical Data Repository, with its conformance measured.

openEHR separates clinical knowledge from software: applications store and query structured health records through a vendor-neutral REST API and the Archetype Query Language. FerroEHR implements that standard natively in Rust: headless, API-first, one self-contained binary on PostgreSQL 18.

Run the quickstart Try the live demo

A server image, a viewer image and a Helm chart on GHCR, built at SLSA Build Level 3, with no JVM and no language runtime, and the openEHR model crates on crates.io.

What it does

The openEHR platform services

Generated from the official machine-readable models, so a specification update is a regeneration, and every service is reached over the openEHR REST API.

ITS-REST 1.1.0

The REST API

EHR, EHR_STATUS, COMPOSITION, DIRECTORY, CONTRIBUTION, query, template and admin resources, in canonical JSON and XML on the wire.

AQL 1.1

The AQL engine

Typed path analysis over a specification-generated Reference Model, compiled to SQL, including ALL_VERSIONS and stored queries.

PostgreSQL 18

Full versioning

Contribution-atomic commits, indelible version history with database-enforced non-overlap, logical delete, attestations and per-version digital signatures.

OPT 1.4

Templates and validation

Template ingestion, WebTemplate generation and deep composition validation against archetype constraints and terminology bindings.

OIDC, SMART and IHE ATNA

Security

OIDC authentication, RBAC and ABAC authorization, SMART App Launch and an IHE ATNA audit trail. One instance per organisation.

Beyond the core

Integration

A change-event feed, EHR Extract messaging, demographics, a FHIR terminology server and S3 multimedia storage connect openEHR to the systems around it.

Conformance

The viewer

See what the API serves

ferroehr-viewer is a web UI for any ITS-REST 1.1.0 CDR. It goes through the public API and never the database, so what you see is exactly what the API serves: queries, templates, EHRs, parties, terminology and the audit log.

Run it

From a laptop to a Kubernetes cluster

The server is one self-contained binary on a minimal distroless image, beside PostgreSQL 18. The viewer is its own image.

Compose

The quickstart

docker-compose.yml ships with every release: docker compose up starts the server and PostgreSQL, and the viewer profile adds the viewer.

OCI images

The container images

ghcr.io/ferrohealth/ferroehr and its PostgreSQL image, for amd64 and arm64, each with SLSA provenance and an SBOM you verify before you run it.

Helm

The chart

oci://ghcr.io/ferrohealth/charts/ferroehr runs the server on Kubernetes, with the cluster hardening guide beside it.

In the family

The product that stores the record

The FerroHEALTH products reach each other only over published protocols. FerroEHR is where the openEHR record lives.

FerroPIX

The patient index FerroEHR asks for the pseudonym an EHR_STATUS subject carries, so identifying data stays outside the clinical record.

FerroTERM and FerroBRIDGE

Coded text is validated on a FHIR terminology server such as FerroTERM, and FHIR mapping and broker delivery live in FerroBRIDGE, a separate server.

FerroFED

The federation gateway sends each member CDR ordinary AQL scoped to its own EHR ids, and FerroEHR answers as a federation node.
